Migration · Oracle Cloud Fusion

Owning the whole data migration

On an ERP rollout, the data migration is usually split across whoever is free that week. On these projects it's mine, end to end: I'm accountable for what lands in Fusion and for whether the business recognises it on day one.

Scope

  • Customers, sites, contacts and account relationships across the TCA model
  • Suppliers, items, price lists and organisation assignments
  • Open AP and AR, GL balances and opening positions
  • Cross-referencing legacy Navision keys to Fusion IDs, kept queryable after go-live

How it runs

Each object has a load that validates first and writes second. State lives in PostgreSQL, so if a run dies halfway through 40,000 records, the next one continues instead of duplicating. Reconciliation queries compare Navision against Fusion after every rehearsal, so the gap list shrinks between cutovers instead of being rediscovered on the night.

A cutover weekend should feel like a checklist, not a rescue.

Also handled

  • Flexfield configuration issues surfaced early, with the functional team
  • Country-specific normalisation between UK and US source data
  • Reconciliation packs the finance leads sign off on, in their own terms

ToolingReusable

Replacing the standard loaders

Oracle's out-of-the-box import tooling works. It just doesn't tell you why it failed. So I built the alternative.

Tooling · Built once, reused per rollout

Migration apps, not migration scripts

Standard spreadsheet-based import templates put the whole burden at the end: you fill in thousands of rows, submit, wait, and get back a rejection file that tells you a row failed without telling you what a human should do about it. On a rollout with several entities that cycle costs days.

What the Python apps do instead

  • Validate before submitting — against the target's own metadata and lookups, so most errors never reach Oracle
  • Track every record — an idempotency ledger means reruns are free and safe
  • Explain failures in business language — "this customer has no billing site" beats a numeric error code
  • Configure per entity — new country, new legal entity, new mapping file; the code doesn't change
  • Survive the next project — the same tooling has been picked up on subsequent rollouts

Engineering constraints I hold myself to

Stable public signatures, payloads that stay byte-identical unless there's a reason not to, and changes split into independent, reviewable changesets. Migration code gets read under pressure at 02:00 — it has to be boring.

Analytics platform · dbt + PostgreSQL

From spreadsheets to a warehouse people trust

The client's own reported figures put revenue growth at 33% in under three years. I won't claim a dashboard sold anything — but the decisions behind that number were made on models I designed and built, and before that they were being made on spreadsheets that disagreed with each other.

What was built

  • A medallion warehouse in dbt over PostgreSQL: raw, conformed, star schema
  • Facts and dimensions covering finance, AP/AR, sales, warehouse and logistics
  • Profitability analysis down to project and employee level
  • Power BI and OTBI on top, with definitions documented and agreed once

The unglamorous half

An intermediate layer materialised as views was forcing expensive multi-join queries to re-execute on every fact build, quietly eating disk and time. Rebuilt as incremental models with a merge strategy. Roughly 2× faster refreshes and a storage problem that stopped being a weekly conversation.

The win isn't the dashboard. It's that two departments finally quote the same figure.

Planning & forecasting

Forecasts you can argue with

Most forecasting dies the same way: it lives in one workbook, on one laptop, with assumptions in someone's head. When the number is questioned, nobody can reconstruct how it was produced, so the discussion becomes about trust instead of about the business.

The approach

  • Drivers and assumptions modelled as data, versioned like anything else
  • Forecast built on the same conformed layer as actuals — so they're comparable by construction
  • Variance tracked over time: not just what we expect, but how wrong we usually are
  • Delivered through Jedox and Power BI, with scenarios the business can run themselves

The point isn't a more accurate number. It's a number whose logic can be opened, challenged and corrected in a meeting.

The reporting pack that builds itself

Small project, disproportionate effect: the weekly status conversation starts from the data instead of from assembling it.
