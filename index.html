Ingestion & migration

Python that survives being run twice.

Loads fail. Networks drop mid-batch. Someone re-sends a corrected file at 19:00 the day before cutover. Every pipeline I write assumes that: state lives in PostgreSQL, so a rerun repeats nothing and skips nothing, and the error report is readable by the person who has to fix the data.

  • Python — requests, zeep, pandas
  • Idempotency ledger in PostgreSQL
  • Custom loaders replacing standard FBDI templates
  • Validation before load, not after
  • Rejects that a functional consultant can act on

Migration · Oracle Cloud Fusion

Owning the whole data migration

On an ERP rollout, the data migration is usually split across whoever is free that week. On these projects it's mine, end to end: I'm accountable for what lands in Fusion and for whether the business recognises it on day one.

Scope

  • Customers, sites, contacts and account relationships across the TCA model
  • Suppliers, items, price lists and organisation assignments
  • Open AP and AR, GL balances and opening positions
  • Cross-referencing legacy Navision keys to Fusion IDs, kept queryable after go-live

How it runs

Each object has a load that validates first and writes second. State lives in PostgreSQL, so if a run dies halfway through 40,000 records, the next one continues instead of duplicating. Reconciliation queries compare Navision against Fusion after every rehearsal, so the gap list shrinks between cutovers instead of being rediscovered on the night.

A cutover weekend should feel like a checklist, not a rescue.

Also handled

  • Flexfield configuration issues surfaced early, with the functional team
  • Country-specific normalisation between UK and US source data

ToolingReusable

Replacing the standard loaders

Oracle's out-of-the-box import tooling works. It just doesn't tell you why it failed. So I built the alternative.

Tooling · Built once, reused per rollout

Migration apps, not migration scripts

Standard spreadsheet-based import templates put the whole burden at the end: you fill in thousands of rows, submit, wait, and get back a rejection file that tells you a row failed without telling you what a human should do about it. On a rollout with several entities that cycle costs days.

What the Python apps do instead

  • Validate before submitting — against the target's own metadata and lookups, so most errors never reach Oracle
  • Track every record — an idempotency ledger means reruns are free and safe
  • Explain failures in business language — "this customer has no billing site" beats a numeric error code
  • Configure per entity — new country, new legal entity, new mapping file; the code doesn't change
  • Survive the next project — the same tooling has been picked up on subsequent rollouts

Engineering constraints I hold myself to

Stable public signatures, payloads that stay byte-identical unless there's a reason not to, and changes split into independent, reviewable changesets. Migration code gets read under pressure at 02:00 — it has to be boring.

From spreadsheets to a warehouse people trust

Planning & forecasting

Forecasts you can argue with

Most forecasting dies the same way: it lives in one workbook, on one laptop, with assumptions in someone's head. When the number is questioned, nobody can reconstruct how it was produced, so the discussion becomes about trust instead of about the business.

The approach

  • Drivers and assumptions modelled as data, versioned like anything else
  • Forecast built on the same conformed layer as actuals — so they're comparable by construction
  • Variance tracked over time: not just what we expect, but how wrong we usually are
  • Delivered through Jedox and Power BI, with scenarios the business can run themselves

The point isn't a more accurate number. It's a number whose logic can be opened, challenged and corrected in a meeting.

The reporting pack that builds itself

Every organisation has one: a recurring report that someone rebuilds manually because it's "only an hour a week". It is never only an hour, and it breaks whenever that person is on holiday.

What it does

  • Pulls project exports out of NetSuite on a schedule into SharePoint
  • Parses the files properly, including the quoted-field edge cases that break naive splitting
  • Groups projects through a mapping the PMO maintains themselves, without touching the flow
  • Applies RAG status rules consistently, so "amber" means the same thing to everyone

Small project, disproportionate effect: the weekly status conversation starts from the data instead of from assembling it.

What came next

SingularityDB

Own project · Desktop app · v0.4

The SQL client I wanted at 02:00

Day-to-day data work jumps between a SQL client, a terminal for dbt and Git. SingularityDB puts the three in one window, with the habits of DBeaver and a few guard rails that are easy to forget when you're tired and the connection says PROD.

What it does

  • PostgreSQL first, plus DuckDB, SQLite and Oracle Fusion (read-only SQL through a BI Publisher report you create once)
  • dbt in its own window: live status for every model and test, lineage down to the column, saved jobs and Git
  • Production is read-only until you unlock it for ten minutes, enforced by the server; writes can be dry-run inside BEGIN … ROLLBACK; an UPDATE with no WHERE asks first
  • Export anywhere: CSV, real .xlsx, JSON, SQL — or straight into a table on another connection (PostgreSQL → DuckDB)
  • No starting over: opens DBeaver projects in place, and shares connections through the project folder without ever sharing passwords
  • Local first: no account, no telemetry, no cloud service
Production should stay read-only until you prove you meant it.

Under the hood

Tauri desktop shell, React and TypeScript, and a small local Node service. macOS and Windows builds, released through GitHub Actions with in-app updates.

macOS toolingOpen source

Publisher templates on a Mac

Design and preview Oracle BI Publisher RTF templates natively on macOS. No Windows virtual machine.

Own project · macOS tooling · Unofficial

BI Publisher templates, without a Windows VM

Oracle's Template Builder for Word only exists on Windows, so anyone on a Mac working on an Oracle Fusion project keeps a virtual machine around just to preview a report. But the engine behind that preview is Java, and Java runs on a Mac.

What you get

  • Template Viewer.app: Oracle's own viewer in your Applications folder, with a modern macOS look: template + XML in, PDF, HTML, Excel or Word out
  • bip-preview: one command from template to opened output, handy while editing in Word for Mac
  • bip-fields: the fields and repeating groups of an XML file, as ready-to-paste tags
  • bip-check: catches open quotes, unclosed for-each/if blocks and fields that aren't in the XML, with suggestions
  • Finder Quick Action: right-click an .rtf and preview it

The careful part

It ships no Oracle software. The installer works from the user's own licensed download of Publisher Desktop, at run time, on their own Mac, and never changes or redistributes Oracle's files. The licensing is spelled out up front, not in a footnote.
